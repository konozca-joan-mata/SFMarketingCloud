Desarrollo & AMPscript

Personalización programática avanzada: AMPscript, SSJS, GTL, APIs, Automation Studio estratégico y Custom Preference Center con CloudPages.

💻 ¿Qué es AMPscript?

AMPscript es el lenguaje de scripting propietario de Salesforce Marketing Cloud, diseñado para incrustar contenido dinámico y lógica de negocio en emails, landing pages y mensajes SMS.

Funciones Fundamentales

  • Lookup(): Recuperar un único valor de una Data Extension externa. Ej: SET @puntos = Lookup("DE_Fidelizacion", "Puntos", "ContactKey", _subscriberkey)
  • LookupRows(): Recuperar múltiples registros de una DE. Devuelve un conjunto de filas iterable con un bucle FOR.
  • IF / ELSEIF / ELSE: Lógica condicional para mostrar u ocultar secciones de contenido según los datos del contacto.
  • Formatting: Cambiar el formato de fechas (FormatDate), números (FormatNumber) o textos (ProperCase para capitalizar nombres).
  • UpsertData(): Escribir o actualizar un registro en una Data Extension desde una landing page de CloudPages.
  • AttributeValue(): Recuperar el valor de un atributo del perfil del suscriptor.
  • Concat(): Concatenar cadenas de texto para construir URLs dinámicas o mensajes.
  • IIF(): If-inline en una sola línea. Equivalente a un operador ternario: IIF(@edad >= 18, "Adulto", "Menor")

Sintaxis y Estructura

  • Delimitadores: El código AMPscript va encerrado entre %%[ y ]%% para bloques de código, o %%= y =%% para expresiones inline.
  • Variables: Se declaran con SET @variable = valor. Los nombres de variable llevan siempre el prefijo @.
  • Comentarios: /* Este es un comentario */ dentro de bloques AMPscript.
  • Merge Fields clásicos: %%FirstName%% para datos básicos sin necesidad de AMPscript (equivale a %%=AttributeValue("FirstName")=%%).
  • Case sensitivity: AMPscript NO distingue mayúsculas de minúsculas en nombres de funciones y variables.

🎯 AMPscript Solutions: Casos de Uso Avanzados

Emails de Fidelización con Puntos en Tiempo Real

  • Escenario: Email que muestra el saldo de puntos del programa de fidelización y calcula la próxima recompensa disponible para cada contacto.
  • Código clave: SET @puntos = Lookup("DE_Fidelizacion", "Puntos", "ContactKey", _subscriberkey)
  • Lógica condicional: IF @puntos >= 500 → mostrar cupón de recompensa. Si no → mostrar barra de progreso hacia el siguiente nivel.
  • Cálculo en tiempo real: SET @faltante = Subtract(500, @puntos) para mostrar cuántos puntos le quedan al contacto.
  • Beneficio: Personalización 1:1 real sin necesidad de pre-generar variantes del email. Un único template sirve para todos los niveles del programa.

Recomendaciones de Productos Personalizadas

  • Escenario: Email que muestra los 3 productos más relevantes para cada contacto, extraídos de una DE de recomendaciones precalculadas por el motor de recomendaciones.
  • Función clave: SET @rows = LookupRows("DE_Recomendaciones", "ContactKey", _subscriberkey)
  • Iteración: FOR @i = 1 TO RowCount(@rows) DO → SET @row = Row(@rows, @i) → renderizar cada producto con sus datos.
  • Datos necesarios en la DE: ContactKey, ProductID, ProductName, ProductImage (URL), ProductURL, ProductPrice.
  • Fallback: Si el contacto no tiene recomendaciones (IF RowCount(@rows) == 0), mostrar productos destacados por defecto de una DE de bestsellers.

Contenido Multiidioma con AMPscript

  • Escenario: Un único template de email que se renderiza en español, inglés, francés u otro idioma según el atributo del contacto.
  • Método con IF: SET @idioma = AttributeValue("Idioma") + bloques IF/ELSEIF que envuelven el contenido en cada idioma.
  • Método con DE de traducciones: SET @texto_cta = Lookup("DE_Traducciones", "Texto", "Clave", "cta_comprar", "Idioma", @idioma). Separa el contenido del código, más fácil de mantener.
  • Ventaja del método DE: El equipo de contenido puede actualizar las traducciones en la DE sin tocar el código AMPscript del email.

Catálogo Dinámico con GTL (Guide Template Language)

  • ¿Cuándo usar GTL en lugar de AMPscript? Cuando necesitas iterar sobre estructuras de datos JSON o mostrar listas de elementos (catálogo, menú, lista de pedidos) de forma más limpia.
  • Sintaxis Handlebars: {{#each products}} ... {{/each}} para iterar. {{product.name}} para acceder a propiedades.
  • Datos desde Content Builder: GTL puede consumir datos de bloques de contenido de tipo "JSON" definidos en Content Builder.
  • Combinación AMPscript + GTL: Es posible usar ambos en el mismo email según las necesidades de cada bloque de contenido.

🔀 Engagement Splits con AMPscript

Combinar AMPscript con Journey Builder permite crear splits basados en el comportamiento del contacto con elementos específicos del email, superando las limitaciones del Engagement Split estándar.

URLs Únicas y Rastreables por Contacto

  • Limitación del Engagement Split estándar: Solo detecta si el contacto hizo clic en cualquier enlace del email. No distingue en qué enlace específico hizo clic.
  • Solución AMPscript: Generar URLs únicas con parámetros que identifiquen la elección del contacto (ej. interés en el producto A o en el producto B).
  • Código ejemplo: SET @urlA = Concat("https://web.com/oferta?sub=", _subscriberkey, "&op=A")
  • Captura en CloudPages: La landing page de destino usa AMPscript para leer el parámetro de la URL y registrar la elección en una DE: UpsertData("DE_Elecciones", 1, "ContactKey", @sub, "Eleccion", @op)
  • Split en Journey: Un Decision Split en JB consulta esa DE (Lookup en el split) para dirigir al contacto al camino correcto según su elección registrada.

Tracking de Preferencias Declaradas en Email

  • Escenario: Email con dos opciones (ej. "Me interesa el Plan Básico / Me interesa el Plan Premium"). El contacto hace clic en una y el journey reacciona en consecuencia.
  • Implementación: Cada botón apunta a una URL única generada con AMPscript que incluye el ContactKey y el identificador de la opción. CloudPages registra la preferencia en MC.
  • Ventaja: El journey puede personalizar todo el flujo posterior (emails, ofertas, asignación de comercial) basándose en una preferencia explícita del contacto, no en inferencias.

🛠️ Herramientas para Desarrolladores

Server-Side JavaScript (SSJS)

  • ¿Qué es? Lenguaje basado en JavaScript clásico (ECMAScript 3), ejecutado en el servidor de MC. Más potente que AMPscript para lógica compleja.
  • Cuándo usarlo: Procesos complejos de transformación de datos, llamadas HTTP a APIs externas, lógica de negocio que AMPscript no puede manejar.
  • Sintaxis clave: Platform.Load("Core", "1"); para cargar librerías. Acceso a objetos de MC como DataExtension, Subscriber, HTTPPost.
  • Dónde se usa: CloudPages (landing pages, formularios avanzados), Script Activity en Automation Studio.
  • Limitación: No se puede usar en cuerpos de email; solo AMPscript y GTL son compatibles con el renderizado de emails en MC.

APIs de Marketing Cloud

  • REST API: Para integraciones modernas: disparar envíos transaccionales (Triggered Sends), gestionar activos de Content Builder, insertar datos en Data Extensions, gestionar journeys y suscriptores.
  • SOAP API: Para operaciones de datos heredadas y de bajo nivel. Usa XML. Muchas operaciones de SOAP están siendo replicadas en REST con mejoras.
  • Autenticación OAuth 2.0: Las llamadas a la API de MC requieren un token de acceso obtenido previamente con Client ID y Client Secret de una App instalada en MC.
  • API de Journey Builder: Permite disparar eventos de entrada a journeys vía API Event (REST), esencial para integraciones en tiempo real desde webs o apps.
  • Marketing Cloud SDKs: SDKs para iOS y Android que facilitan la integración de aplicaciones móviles con MC para push notifications y gestión de preferencias.

Developer Resources

  • Marketing Cloud Developer Center: Documentación oficial completa de todas las funciones AMPscript, SSJS, REST y SOAP API.
  • AppExchange: Marketplace de aplicaciones y conectores de terceros para extender las capacidades de MC sin desarrollo a medida.
  • Postman Collections: Salesforce publica colecciones de Postman con todas las llamadas REST de MC pre-configuradas para facilitar el desarrollo y testing.
  • SSJS Playground: Herramientas de la comunidad para testear código SSJS sin necesidad de desplegarlo en producción.

⚙️ Marketing Automation: Estrategias Avanzadas

La automatización eficiente combina datos de primera parte, plantillas reutilizables y flujos bien definidos para escalar el marketing sin escalar el equipo.

Pilares de una Estrategia de Automatización Sólida

  • First-Party Data: Priorizar los datos propios (comportamiento web, historial de compras, preferencias declaradas) sobre datos de terceros. Son más precisos y resistentes a cambios regulatorios como la eliminación de cookies de terceros.
  • Plantillas reutilizables: Diseñar emails, journeys y automations que se puedan clonar y adaptar fácilmente. Una buena plantilla de welcome series sirve para múltiples segmentos de producto.
  • Modularidad: Construir automations con actividades pequeñas y bien nombradas, en lugar de monolitos. Más fácil de debuguear, modificar y reutilizar.
  • Naming conventions: Establecer convenciones claras para carpetas, DEs y automations: [TipoNegocio]_[Funcion]_[Frecuencia] (ej. "MKTG_SegmentacionVIP_Daily").
  • Monitorización: Revisar regularmente el historial de ejecución de automations en Automation Studio para detectar errores antes de que escalen a problemas de datos.

Patrones de Integración con FTP / SFTP

  • File Drop Pattern (más común): Sistema externo deposita un archivo CSV en el SFTP de MC → File Drop Automation se activa → Import File Activity carga los datos a una DE → SQL Query los procesa → Journey Entry arranca.
  • Scheduled Import Pattern: Sin File Drop; una Automation programada (ej. cada noche a las 01:00) busca el archivo en el FTP con un nombre predecible y lo importa.
  • Scheduled Export Pattern: Automation nocturna extrae datos de rendimiento de MC con Data Extract Activity → los deposita en el SFTP → sistema de BI externo los consume cada mañana.
  • Naming de archivos con timestamp: Usar timestamps en los nombres de archivo para evitar sobrescrituras y facilitar la auditoría (ej. leads_20260101_0200.csv).

SQL en Automation Studio: Mejores Prácticas

  • Overwrite vs. Append vs. Update: Al configurar un Query Activity, elegir correctamente si la DE destino debe sobrescribirse completamente, añadir filas o actualizar registros existentes.
  • Performance: Las queries en MC se ejecutan sobre un motor SQL con limitaciones. Evitar SELECT * y JOINs innecesarios. Usar índices (primary keys) siempre que sea posible.
  • Manejo de duplicados: Usar DISTINCT o ROW_NUMBER() OVER (PARTITION BY ContactKey ORDER BY FechaCompra DESC) para asegurar registros únicos por contacto.
  • Variables de fecha dinámicas: DATEADD(DAY, -30, GETDATE()) para crear segmentos de los últimos N días sin tener que actualizar la query cada día.
  • Testing: Probar primero con una DE de prueba y pocos registros antes de ejecutar sobre las DEs de producción.

🎛️ Custom Preference Center con CloudPages

El Subscription Center por defecto de MC es funcional pero genérico. CloudPages + AMPscript permiten crear un preference center completamente personalizado, de marca y con experiencia de usuario superior.

¿Qué es CloudPages?

  • Definición: Módulo de MC para crear landing pages, microsites, formularios y páginas interactivas alojadas en los servidores de Salesforce.
  • Casos de uso: Preference centers, páginas de confirmación de opt-in, formularios de captura de leads, páginas de aterrizaje de campañas, portales de cliente básicos.
  • Tecnología: HTML + CSS + AMPscript (o SSJS) + JavaScript en el cliente. Se pueden usar frameworks CSS (Bootstrap, Tailwind) via CDN.
  • Dominio personalizado: MC provee un dominio por defecto, pero se puede configurar un subdominio propio (ej. preferencias.tumarca.com).

Arquitectura del Preference Center Personalizado

  • DE de Preferencias: Una Data Extension con ContactKey, Email, y un campo booleano por cada categoría de comunicación (ej. NewsletterSemanal, OfertasPromocion, NovedadesProducto).
  • Publication Lists: Listas de suscripción en MC que corresponden a cada categoría. El estado de suscripción en Publication Lists determina si el contacto recibe o no cada tipo de comunicación.
  • Enlace desde email: Sustituir el enlace del Subscription Center por defecto con una URL de CloudPages que incluye el ContactKey encriptado como parámetro: %%=RedirectTo(CloudPagesURL(ID_pagina, "ck", _subscriberkey))=%%

Implementación Paso a Paso

  • Paso 1 — Leer preferencias actuales: Al cargar la página, usar SET @ck = RequestParameter("ck") para obtener el ContactKey de la URL. Luego Lookup() para leer el estado actual de cada suscripción y pre-marcar los checkboxes del formulario.
  • Paso 2 — Formulario HTML: Un checkbox por cada categoría de comunicación. El atributo name y value de cada checkbox corresponde a la categoría en la DE.
  • Paso 3 — Guardar respuestas: Al enviar el formulario, AMPscript usa UpsertData() para actualizar la DE de preferencias con las selecciones del usuario.
  • Paso 4 — Actualizar Publication Lists: Usar SetObjectProperty() e InvokeUpdate() en AMPscript (o el objeto Subscriber en SSJS) para actualizar el estado de suscripción en cada Publication List según las nuevas preferencias.
  • Paso 5 — Confirmar: Mostrar un mensaje de confirmación en la misma página o redirigir a una página de agradecimiento.

Casos de Uso del Preference Center

  • Centro de preferencias de comunicación: El usuario elige qué tipo de emails recibir (newsletter, ofertas, eventos, novedades de producto) en lugar de darse de baja de todo.
  • Actualización de datos del perfil: El usuario puede corregir su nombre, empresa o ciudad directamente, actualizando la DE de contactos.
  • Gestión de frecuencia: El usuario elige con qué frecuencia quiere recibir comunicaciones (diario, semanal, mensual) y MC adapta el envío.
  • Opt-in a SMS o WhatsApp: Añadir canales adicionales al preference center para capturar el consentimiento de nuevos canales de forma explícita y documentada.

🚀 Soluciones con Código: Ejemplos Combinados

Ejemplos de Aplicación

  • Email de renovación de suscripción: Muestra el plan actual del usuario, la fecha de vencimiento calculada con AMPscript, el precio de renovación (con descuento calculado si es cliente VIP) y un CTA con URL única para el pago.
  • Portal de seguimiento de pedido: CloudPage que el usuario visita desde el email de confirmación. AMPscript lee el ID de pedido de la URL y muestra el estado, fecha estimada y productos del pedido desde una DE de pedidos.
  • Encuesta post-compra: Email con 3 opciones de valoración (1, 2, 3 estrellas) como URLs únicas. El clic registra la valoración en una DE. Journey reacciona con un follow-up diferente según la puntuación dada.
  • Código de descuento único: Cada contacto recibe un código de descuento único generado por AMPscript (Lookup desde una DE de códigos asignados previamente), evitando que los códigos se compartan.
